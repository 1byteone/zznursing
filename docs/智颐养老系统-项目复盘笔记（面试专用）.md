**核心代码设计**：

```java
// 1. ThreadLocal工具类
public class UserThreadLocal {
    private static final ThreadLocal<Long> LOCAL = new ThreadLocal<>();

    public static void set(Long userId) {
        LOCAL.set(userId);
    }

    public static Long getUserId() {
        return LOCAL.get();
    }

    public static void remove() {
        LOCAL.remove();  // 防止内存泄漏
    }
}

// 2. 拦截器
@Component
public class MemberInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(...) {
        // 解析Token，存储用户ID
        Long userId = parseToken(token);
        UserThreadLocal.set(userId);
        return true;
    }

    @Override
    public void afterCompletion(...) {
        // 必须清理，防止内存泄漏
        UserThreadLocal.remove();
    }
}

// 3. Controller使用
@GetMapping("/my-reservations")
public R<List<Reservation>> getMyReservations() {
    Long userId = UserThreadLocal.getUserId();  // 直接获取
    return R.ok(reservationService.getByUserId(userId));
}
```

**内存泄漏问题解决**：

```
问题原因：
1. ThreadLocal的生命周期与线程相同
2. Tomcat使用线程池，线程会被复用
3. ThreadLocal中的数据不会自动清理
4. 导致内存泄漏和数据污染

解决方案：
1. 在拦截器afterCompletion中调用remove()
2. 无论请求成功或失败，都会执行清理
3. 使用try-finally确保清理
```

#### R（结果）

```
技术成果：
- 登录成功率99.9%+
- Token认证响应时间<10ms
- 内存泄漏问题完全解决

业务价值：
- 家属登录体验流畅
- 自动注册减少用户操作
- 用户信息传递便捷
```

#### 深挖问题准备

**Q：ThreadLocal原理是什么？**

```
1. 每个Thread对象内部维护一个ThreadLocalMap
2. ThreadLocalMap的Key是ThreadLocal对象，Value是存储的值
3. 不同线程访问同一个ThreadLocal，获取的是各自线程的值
4. Key是弱引用，Value是强引用

内存泄漏原因：
- Key是弱引用，会被GC回收
- 但Value是强引用，不会自动回收
- 线程池复用时，Value一直存在
- 必须手动调用remove()清理
```

**Q：为什么必须调用remove()？**

```
1. 线程池复用问题：
   - Tomcat使用线程池处理请求
   - 线程处理完请求后不会销毁，而是回到线程池
   - ThreadLocal中的数据不会自动清理

2. 内存泄漏：
   - ThreadLocalMap的Value是强引用
   - 不清理会一直占用内存
   - 大量请求后可能OOM

3. 数据污染：
   - 线程被复用后，可能获取到上一个用户的数据
   - 导致用户A看到用户B的数据（严重安全问题）
```

### 4.2 技术深度问题

**Q：Redis在项目中的应用场景？**

```
1. 健康评估模块：
   - 缓存PDF内容（Hash结构）
   - Key: healthReport, Field: 身份证号, Value: PDF文本
   - 过期时间：24小时

2. 设备管理模块：
   - 缓存产品列表（String结构）
   - 缓存设备最新数据（Hash结构）

3. 系统模块：
   - 缓存字典数据
   - 缓存用户Token
   - 分布式锁

缓存策略：
- 读穿透：先读缓存，miss则读DB并回写
- 写穿透：先更新DB，再删除缓存
- 过期策略：根据数据变化频率设置
```

**Q：如何保证接口幂等性？**

```
1. Token机制：
   - 每次请求携带Token
   - 服务端校验Token有效性

2. 唯一索引：
   - 数据库层面保证唯一性
   - 如：设备名称、设备标识

3. 分布式锁：
   - Redis SETNX实现
   - 防止并发重复提交

4. 业务层校验：
   - 查询是否已存在
   - 存在则返回或更新
```

**Q：如何处理分布式事务？**

```
当前方案：
- 本地事务 + 补偿机制
- 如：设备注册失败，调用华为云删除接口

改进方案：
1. 消息队列最终一致性
   - 发送消息到MQ
   - 消费者处理，失败则重试
   - 达到最大重试次数则人工处理

2. Seata分布式事务
   - AT模式：无侵入
   - TCC模式：高性能
```

### 4.3 场景设计问题

**Q：如何设计一个高并发的健康评估接口？**

```
1. 缓存层：
   - Redis缓存PDF内容
   - Redis缓存AI分析结果（相同报告）

2. 异步处理：
   - 提交评估请求 → 返回任务ID
   - 异步调用AI → 存储结果
   - 前端轮询结果

3. 限流：
   - 令牌桶限流
   - 防止AI接口被刷

4. 降级：
   - AI服务不可用时，返回默认评估结果
   - 或提示用户稍后重试

5. 监控：
   - 接口响应时间监控
   - AI调用成功率监控
```

**Q：如何设计设备数据实时推送？**

```
当前方案：AMQP长连接

优化方案：
1. WebSocket：
   - 服务端主动推送
   - 实时性更高

2. SSE（Server-Sent Events）：
   - 单向推送
   - 实现简单

3. 消息队列：
   - 设备数据 → MQ → 消费者 → WebSocket推送

架构：
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ IoT设备 │───>│ 华为云  │───>│ AMQP    │───>│ WebSocket│
│         │    │ IoT平台 │    │ 消费者  │    │ 推送    │
└─────────┘    └─────────┘    └─────────┘    └─────────┘
```
