## 1. 项目一句话介绍

### 1.1 30 秒版本

智颐养老系统是一个面向养老院场景的综合管理平台，包含后台管理端和微信小程序端，主要解决老人入住、护理服务、健康评估、家属登录查询以及智能设备接入等问题，帮助养老机构提升护理效率、减少人工统计成本，并增强对老人健康状态的数字化管理能力。

### 1.2 1 分钟版本

这是一个基于 `Spring Boot + Vue + MyBatis-Plus + MySQL + Redis` 搭建的养老院业务系统。系统分为两部分：  
一部分是后台管理端，供机构工作人员处理老人档案、入住办理、护理等级、护理计划、合同和设备管理；  
另一部分是面向家属的小程序端，支持微信登录、预约、房型查询等能力。  

在这个项目里，比较有代表性的技术点主要有四类：

1. **健康评估模块**：把老人上传的 PDF 体检报告解析后交给百度千帆大模型做结构化分析，再将风险等级、健康分数、异常指标和建议结果落库；
2. **微信小程序登录模块**：基于微信 `code` 换取 `openid`，再获取手机号，结合 JWT 和 `ThreadLocal` 完成前台用户认证；
3. **IoT 设备接入模块**：对接华为云 IoTDA，支持产品同步、设备注册、设备影子查询，并通过 AMQP 异步接收设备上报数据；
4. **基础性能优化**：利用 Redis 缓存护理等级、护理计划、IoT 产品列表等高频读数据，并通过定时任务维护合同状态。

## 2. 项目定位与业务价值

## 2.1 项目服务对象

- **后台用户**：养老院管理员、护理员、运营人员
- **前台用户**：老人家属
- **外部系统**：微信开放平台、百度千帆大模型、华为云 IoTDA、阿里云 OSS

## 2.2 要解决的核心问题

### 业务层面

- 传统养老院数据分散，老人档案、入住、护理计划、合同、设备数据分开管理；
- 家属获取老人健康情况和服务信息不够及时；
- 老人体检报告解读强依赖人工，效率低且标准不一致；
- 智能手环、智能床垫等设备接入后，如果没有统一平台，数据难以汇总和使用。

### 系统层面

- 需要一套统一后台承接“入住 + 护理 + 健康 + 设备”业务；
- 需要一套前台认证机制支持家属端访问；
- 需要把第三方 AI 和 IoT 能力接入到现有业务系统中；
- 需要在不做微服务拆分的前提下，先把核心链路跑通并保证可维护性。

## 2.3 项目业务价值

- 把老人从“预约/入住/护理/健康评估/设备监测”串成闭环；
- 让家属可以通过小程序查询与预约，降低线下沟通成本；
- 让健康评估从人工经验判断转向“AI 辅助分析”；
- 让设备上报数据能进入业务系统，为后续预警和分析提供基础。

家属小程序 / 后台管理端
          ↓
      Controller
          ↓
       Service
          ↓
   MyBatis-Plus / Mapper
          ↓
     MySQL + Redis
          ↓
┌───────────────┬───────────────┬───────────────┐

└───────────────┴───────────────┴───────────────┘

## 3.4 为什么这样设计

### 为什么是单体而不是微服务

- 当前业务复杂度还处于“一个业务域内多模块协同”的阶段；
- 先做单体可以降低部署、联调、事务一致性、排障复杂度；
- 养老业务本身对“流程稳定落地”优先级高于“服务拆分炫技”。

### 为什么用 Redis

- 护理等级、护理项目、护理计划属于典型高频读低频写数据；
- IoT 产品列表来自第三方云平台，没必要每次都远程查；
- 健康评估里 PDF 文本是一次上传、多次使用，适合短期缓存；
- 登录态、限流、防重复提交等基础能力本身就依赖 Redis。

### 为什么用 JWT + 自定义拦截器

- 小程序端天然不适合传统 Session；
- JWT 天然适合无状态认证；
- 再配合 `MemberInterceptor + ThreadLocal` 可以让业务代码方便拿到前台用户 ID。

### 为什么 AI 调用放在业务服务层

- 当前业务目标是先快速落地“体检报告自动分析”；
- 把 AI 调用封装成 `AIModelInvoker`，可以避免控制层直接依赖第三方 SDK；
- 后续如果替换模型，只需要调整配置和调用封装层即可。

## 4. 核心业务流程

## 4.1 老人入住主链路

```text
后台提交入住申请
  ↓
校验老人是否已入住
  ↓
更新床位状态为已入住
  ↓
保存或更新老人档案
  ↓
生成合同编号并创建合同
  ↓
写入入住记录
  ↓
写入入住配置（床位、护理等级、起止时间）
```

### 面试表达重点

- 这条链路体现了**典型的多表业务事务**；
- 涉及 `elder`、`bed`、`contract`、`check_in`、`check_in_config` 多张表；
- 重点不是“增删改查”，而是“如何保证入住流程数据完整、状态一致”。

## 4.2 健康评估主链路

```text
上传 PDF 体检报告
  ↓
文件上传到 OSS
  ↓
PDF 解析成文本
  ↓
按身份证号写入 Redis Hash（24 小时过期）
  ↓
提交健康评估表单
  ↓
拼接 Prompt 调用百度千帆
  ↓
返回结构化 JSON
  ↓
解析健康分数、风险等级、异常项、建议
  ↓
落库保存健康评估结果
```

### 面试表达重点

- 核心不是“调用了 AI”，而是**如何让 AI 输出能稳定接进业务系统**；
- 这里做了三件事：**报告预处理、Prompt 约束、结构化落库**。

## 4.3 小程序登录主链路

```text
小程序发起登录
  ↓
前端 code 换 openid
  ↓
调用微信接口获取手机号
  ↓
查询家属是否已存在
  ↓
不存在则自动注册，存在则更新手机号
  ↓
生成 JWT token
  ↓
后续请求带 token
  ↓
拦截器解析 token，userId 放入 ThreadLocal
  ↓
业务代码读取当前用户 ID
```

## 4.4 IoT 设备接入链路

```text
后台同步产品列表
  ↓
Redis 缓存 IoT 产品信息
  ↓
后台注册设备
  ↓
先校验名称/节点号/绑定位置唯一性
  ↓
调用华为云 IoTDA 创建设备
  ↓
本地保存设备信息与密钥
  ↓
设备上报数据到 IoTDA
  ↓
本系统通过 AMQP 异步消费消息
  ↓
解析上报数据并批量入库
```

## 5. 模块一：健康评估（最适合深挖）

## 5.1 业务背景

养老院在接收老人入住前，往往需要参考体检报告判断其健康状况、风险等级以及推荐护理等级。  
如果完全依赖人工解读，会有三个问题：

- 专业门槛高，必须依赖医护经验；
- 报告内容多，人工逐项分析耗时长；
- 不同人员的判断标准可能不一致。

所以这个模块的目标不是“替代医生”，而是做一个**AI 辅助分析工具**，帮助系统快速产出结构化健康结论。

## 5.2 实际实现方案

### 第一步：上传 PDF 并做预处理

- 用户上传体检报告 PDF；
- 文件先上传到阿里云 OSS；
- 后端用 `PDFUtil.pdfToString()` 将 PDF 解析成纯文本；
- 以 `healthReport` 作为 Redis Hash Key，以老人身份证号作为 field，缓存解析后的报告文本；
- TTL 设置为 `24 小时`。

### 第二步：提交评估请求

- 业务表单里带上老人基本信息，尤其是身份证号；
- 服务层根据身份证号去 Redis 中拿到报告文本；
- 如果 Redis 没有对应数据，直接抛业务异常，提示先上传报告。

### 第三步：构造强约束 Prompt

这里的设计重点不是“让 AI 自由发挥”，而是强制它输出系统能接住的结构化 JSON。

Prompt 中明确要求输出：

- 总检日期
- 健康评估结果（风险等级、健康指数）
- 风险分布
- 异常数据列表
- 八大系统评分
- 总结

并且要求：

- 只能输出 JSON
- 不要夹带解释性文字
- 字段名固定

### 第四步：AI 返回后做结构化落库

AI 返回 JSON 后，系统会反序列化成 `HealthReportVo`，再写回业务表：

- 通过身份证号解析出生日期、年龄、性别；
- 取 AI 生成的健康分数；
- 取风险等级；
- 根据健康分数映射护理等级名称；
- 生成是否建议入住标记；
- 把异常分析、系统评分、风险分布序列化为 JSON 字符串落库。

## 5.3 为什么这个设计合理

### 为什么要先把 PDF 文本放 Redis，而不是直接同步处理

- PDF 解析是一次性动作，不需要每次重复做；
- 上传和提交评估在交互上是两个动作，拆开更符合前端流程；
- Redis 作为临时缓存可以减少中间状态落库的复杂度；
- 用“身份证号”做索引，业务上容易理解，也方便后续评估请求关联。

### 为什么不让前端直接调用 AI

- 体检报告属于敏感数据，不能把 AI Key 暴露给前端；
- 后端统一做 Prompt、结构校验、异常处理、审计更安全；
- 后续如果切换模型、增加重试、加兜底都更可控。

### 为什么用结构化 JSON 而不是纯文本结果

- 纯文本很难直接落表；
- 前端渲染和后端统计都需要结构化字段；
- 结构化输出更容易做兜底校验与后续分析。

## 5.4 这个模块最值得讲的技术点

### 技术点 1：Prompt 工程不是“写一句提示词”

这个模块真正体现能力的地方，是把业务问题拆成机器可执行的输出协议：

- 风险等级枚举化；
- 异常指标列表字段固定化；
- 总结文本单独抽取；
- 八大系统评分结构化。

面试时可以说：

> 我不是直接把 PDF 内容扔给模型，而是先把业务需要落库的字段设计出来，再反推 Prompt，让模型以固定 JSON 输出，降低了解析失败率。

### 技术点 2：AI 结果和业务规则结合

AI 只是产出基础分析结果，真正业务决策还需要后端补充规则：

- 根据健康分数推导护理等级；
- 根据分数判断是否建议入住；
- 根据身份证号补齐年龄、性别、出生日期。

面试时可以说：

> 我没有把所有决策都交给大模型，而是让 AI 做“认知型分析”，把确定性强的规则仍然放在后端，避免业务规则漂移。

### 技术点 3：异常处理清晰

当前实现里已经覆盖了两个关键失败点：

- 上传后未提交或缓存过期；
- AI 调用前找不到报告文本。

这可以延伸讲到你的工程意识：

> AI 模块不只是“调成功一次”，还要考虑中间状态过期、解析失败、异常重试、用户重新上传等完整链路。

## 5.5 这个模块的不足与可优化点

这部分非常适合拿来做“主动承认 + 给出改法”的加分项。

### 当前不足

- Redis Key 设计较简单，使用固定 Hash `healthReport`，适合当前规模，但隔离性一般；
- 没有对 AI 返回 JSON 做二次字段校验；
- 没有做失败重试或降级；
- 没有把 AI 响应耗时、成功率做指标化埋点；
- 没有做历史报告版本管理。

### 可优化方案

1. Redis Key 改成更细粒度格式，例如 `health:report:{idCard}`；
2. 对 AI 返回结果做 JSON Schema 校验；
3. 增加重试机制和兜底提示；
4. 把 AI 响应时间、失败率、命中率纳入监控；
5. 对报告解析和 AI 分析拆异步任务，提升大文件处理体验。

## 5.6 这个模块可以怎么回答面试官

### 问：你们为什么要引入 AI？

答法：

> 不是为了炫技，而是因为体检报告解读是典型的“规则多、文本多、专业性强”的场景，纯人工效率低，而且结论不统一。AI 在这个场景里最适合承担的是“辅助分析”和“结构化提取”。

### 问：你怎么保证 AI 输出稳定？

答法：

> 我主要从三层控制：第一层是 Prompt 强约束，只允许输出固定 JSON；第二层是 SDK 侧指定 JSON 响应格式；第三层是后端反序列化后再用业务规则补齐和校验，避免模型自由输出直接影响主业务。

### 问：为什么用 Redis 缓存体检报告文本？

答法：

> 因为报告上传和评估提交是两个阶段，PDF 解析一次就够了，不需要每次提交都重新解析。放 Redis 可以减少重复 I/O，也避免为了一个临时中间结果单独设计数据库表。

## 6. 模块二：微信小程序登录（很适合讲认证设计）

## 6.1 业务背景

系统不仅有后台管理端，还有给家属使用的小程序端。  
小程序端的用户体系和后台管理员体系是隔离的，所以不能直接复用后台登录逻辑。

这个场景的主要难点有：

- 小程序没有传统 Web 的 Cookie/Session 使用体验；
- 登录第一步是微信 `code` 换 `openid`；
- 用户第一次登录时系统中并没有本地账号；
- 后续接口又要能方便拿到当前前台用户。

## 6.2 实际实现流程

### 第一步：根据 `code` 获取 `openid`

- 小程序端先拿微信登录 `code`；
- 后端调用微信 `jscode2session` 接口获取 `openid`。

### 第二步：根据手机号补全家属信息

- 后端再通过微信接口获取用户绑定手机号；
- 以 `openid` 作为唯一身份标识；
- 如果数据库里已有家属，则更新手机号；
- 如果没有，则自动创建新用户，并生成一个随机昵称。

### 第三步：生成 JWT

- 把 `userId`、`nickName` 放入 claims；
- 通过 `TokenService.createToken()` 生成 JWT；
- 返回给前端。

### 第四步：请求拦截与上下文透传

- 小程序后续请求把 token 放在请求头 `authorization` 中；
- `MemberInterceptor` 在 `preHandle` 中解析 token；
- 取出 `userId` 放入 `UserThreadLocal`；
- 业务代码通过 `UserThreadLocal.getUserId()` 直接读取当前用户；
- 请求结束后在 `afterCompletion` 里执行 `remove()`，避免线程复用导致脏数据或内存泄漏。

## 6.3 为什么这个方案合理

### 为什么不直接用 Session

- 小程序端更适合 token 化认证；
- 前后端分离场景中，JWT 更利于跨端调用；
- 服务端不必强依赖 session 存储。

### 为什么还要配合 ThreadLocal

- Controller 和 Service 很多时候只关心“当前是谁”，不想层层传 userId；
- 用 `ThreadLocal` 可以让业务代码更简洁；
- 但一定要记得请求结束后清理，这里通过 `afterCompletion` 做了回收。

### 为什么前台用户和后台用户体系分开

- 后台是机构人员，前台是家属，权限模型完全不同；
- 分开后更容易做资源隔离、接口隔离和认证隔离；
- 面试时这能体现你有基本的权限边界意识。

## 6.4 这个模块最值得讲的技术点

### 技术点 1：登录即注册

这个设计解决了小程序用户“第一次进来系统没账号”的问题。

好处：

- 降低注册流程复杂度；
- 用户体验更顺滑；
- 后台不需要提前给家属建账号。

### 技术点 2：ThreadLocal 生命周期控制

很多人面试只会说“我用了 ThreadLocal”，但真正加分的是你要能讲出风险：

- Tomcat/线程池会复用线程；
- 如果不清理，前一个请求的数据可能串到后一个请求；
- 所以必须在 `afterCompletion` 中 `remove()`。

### 技术点 3：前台接口只拦 `/member/**`

`ResourcesConfig` 里对小程序端接口做了单独拦截规则，只排除了登录和少量公开接口。  
这说明你不是简单地“全局套一个鉴权”，而是做了接口级边界划分。

## 6.5 可优化点

### 当前不足

- 微信 access_token 每次实时获取，没有本地缓存；
- token 里只放了少量字段，没有做更完整的前台用户会话治理；
- 自动生成昵称规则较简单；
- 没有显式做前台 token 刷新策略。

### 可优化方案

1. 把微信 access_token 缓存到 Redis，减少重复调用；
2. 引入前台用户登录态续期机制；
3. 增加家属和老人关系绑定校验；
4. 对敏感操作增加短信或二次校验。

## 6.6 这个模块面试怎么讲

> 小程序端我采用的是 `微信 code -> openid -> 手机号 -> 本地用户 -> JWT` 这条链路。  
> 后续请求通过拦截器解析 token，把 `userId` 放入 `ThreadLocal`，这样业务代码就不需要层层传参。  
> 这个模块最大的细节其实不是登录成功，而是 ThreadLocal 的生命周期管理，我在请求结束后做了 `remove()`，避免线程复用导致脏数据。

## 7. 模块三：IoT 设备接入（非常适合拉开差距）

## 7.1 业务背景

养老场景里会接入智能手环、床垫、定位设备等，系统不仅要能管理设备，还要能消费设备上报数据。  
如果只是做设备台账，价值不大；真正的业务价值在于：

- 设备与老人、房间、床位建立绑定关系；
- 平台能实时拿到设备状态和属性；
- 上报数据能进入业务系统，为健康监测和预警提供基础。

## 7.2 实际实现内容

### 功能一：同步 IoT 产品列表

- 后端调用华为云 IoTDA 的 `listProducts`；
- 把产品列表缓存到 Redis Key `iot:all_product_list`；
- 后续设备注册时直接读取缓存供前端选择。

### 功能二：设备注册

设备注册前做了三类校验：

1. 设备名称不能重复；
2. 设备标识 `nodeId` 不能重复；
3. 同一位置不能绑定同一产品，防止重复占位。

校验通过后：

- 调用 IoTDA 的 `addDevice` 创建设备；
- 生成设备密钥 `secret`；
- 把设备云端 ID、本地绑定关系、产品信息一起落库。

### 功能三：设备详情与影子数据查询

- 通过 IoTDA 查询设备详情；
- 获取设备在线状态、激活时间；
- 获取设备影子 `reported` 属性；
- 统一转换时间时区并封装给前端。

### 功能四：AMQP 异步消费设备上报数据

系统启动后会创建 AMQP 连接：

- 使用 `ApplicationRunner` 在启动时拉起消费者；
- 支持多连接配置；
- `MessageListener` 收到消息后，提交到线程池异步处理；
- 解析 `notify_data`；
- 再交给 `deviceDataService.batchInsertDeviceData()` 做批量入库。

## 7.3 为什么这样设计

### 为什么同步产品列表后放 Redis

- 产品元数据变更频率低；
- 来自第三方平台，远程查询成本高；
- 设备注册页面需要频繁展示产品列表；
- 缓存后能减少外部 API 调用次数并提升页面响应速度。

### 为什么设备注册前要做三重校验

- 设备名称重复会影响运维识别；
- `nodeId` 重复会导致设备唯一性失真；
- 同位置重复绑定同产品会造成业务映射混乱。

### 为什么 AMQP 处理还要进线程池

- `onMessage` 回调中不适合做重逻辑；
- 如果直接同步处理，消费吞吐会下降；
- 使用线程池可把“消息接收”和“业务处理”解耦。

## 7.4 这个模块最有价值的讲法

### 技术点 1：本地业务模型和云端设备模型映射

设备不只是“云上有一台设备”，本地系统还要知道：

- 它属于哪个产品；
- 绑定的是老人还是房间/床位；
- 设备的物理位置类型是什么；
- 云端 ID 和本地业务 ID 如何关联。

这说明你考虑的是“设备如何进入业务系统”，不是只会调 SDK。

### 技术点 2：实时数据接入链路

这个模块最能打动面试官的点是：

> 我们不是只做设备增删改查，而是把 IoT 平台上报数据通过 AMQP 拉回到本地系统，并用异步线程池处理，形成完整的数据接入链路。

### 技术点 3：时区转换

云端返回的是 UTC 时间，系统做了转上海时区处理。  
这个细节看起来不大，但很能体现你处理第三方平台集成时的工程完整性。

## 7.5 不足与改进

### 当前不足

- 设备“云端创建成功、本地保存失败”存在一致性风险；
- 产品列表缓存没有过期策略和主动刷新机制；
- 上报数据消费缺少幂等控制和重放保护；
- 没有做消息积压监控。

### 面试时非常推荐主动说的优化方案

1. 设备注册引入补偿逻辑：本地失败时回滚云端设备；
2. 或者通过消息队列 / 本地事件表实现最终一致性；
3. 上报数据增加设备 ID + 时间戳维度的幂等设计；
4. 对关键指标做监控：消费速率、失败率、延迟。

## 8. 支撑型模块：入住、护理计划、缓存、定时任务

这部分不一定要长讲，但非常适合在面试官追问“还有别的业务模块吗”时补充。

## 8.1 入住办理

### 亮点

- 入住不是单表操作，而是多表联动；
- 一次申请会联动床位、老人、合同、入住记录、入住配置；
- 业务上体现的是“老人正式进入院内服务体系”。

### 面试讲法

> 入住模块我更关注的是业务一致性。因为入住不是简单插一条记录，而是多个实体状态同步变化，比如床位状态、老人状态、合同状态、护理等级配置都要跟着变化。

## 8.2 护理等级 / 护理项目 / 护理计划

### 实际做法

- 这几类基础数据读多写少；
- 写操作后删缓存；
- 读操作先查 Redis，未命中再查 DB 并回填。

### 面试亮点

- 这是典型的**旁路缓存模式**；
- 不是盲目上缓存，而是针对高频基础元数据；
- Key 设计清晰：`nursingLevel:all`、`nursingProject:all`、`nursingPlan:all`。

### 可以主动补一句

> 这里我用的是“更新数据库后删除缓存”的策略，适合当前业务规模。如果后续并发更高，可以再考虑延迟双删或者基于消息的缓存失效通知。

## 8.3 合同状态定时更新

### 实际做法

- 通过定时任务扫描状态为待生效、且时间已到的合同；
- 批量更新为生效中。

### 适合怎么讲

> 这个任务体现的是“时间驱动型业务状态流转”。有些状态变化不是靠用户点击触发，而是靠系统定时推进，比如合同从未生效变为生效中。

## 10. 高频面试问题与标准答法

## 10.1 你先介绍一下这个项目

答法：

> 智颐养老系统是一个面向养老院场景的管理平台，分后台管理端和家属小程序端。后台主要负责老人入住、护理等级、护理计划、健康评估、设备管理和合同管理；小程序端主要支持家属微信登录、预约和信息查询。  
> 我主要参与了健康评估、微信小程序登录、IoT 设备接入以及部分入住业务链路开发。项目技术栈是 Spring Boot、MyBatis-Plus、MySQL、Redis，并对接了百度千帆、微信开放平台和华为云 IoTDA。

## 10.2 你这个项目里最有亮点的模块是什么

答法：

> 我觉得最有代表性的有三个：  
> 第一是健康评估模块，我把 PDF 体检报告解析后交给 AI 做结构化分析；  
> 第二是小程序登录模块，做了微信登录、JWT 和 ThreadLocal 上下文透传；  
> 第三是 IoT 设备接入模块，对接华为云并通过 AMQP 接收设备上报数据。

## 10.3 Redis 在项目里用在哪

答法：

> Redis 主要有四类用途：  
> 一类是基础框架层，比如登录态、限流、防重复提交；  
> 一类是业务基础数据缓存，比如护理等级、护理项目、护理计划；  
> 一类是第三方产品数据缓存，比如 IoT 产品列表；  
> 还有一类是 AI 中间数据缓存，比如体检报告 PDF 解析后的文本，按身份证号临时缓存 24 小时。

## 10.4 你们怎么处理缓存一致性

答法：

> 目前主要采用的是“读缓存、写数据库、删缓存”的旁路缓存方案。因为护理等级、护理计划这些数据写频率低，这种模式足够简单稳定。后续如果并发进一步增大，可以考虑延迟双删或消息通知式失效。

## 10.5 为什么小程序登录要用 ThreadLocal

答法：

> 因为后续很多业务接口都需要当前用户 ID，如果每层都手动传会比较啰嗦。拦截器解析 token 后把 `userId` 放入 ThreadLocal，Controller 和 Service 就可以直接拿到当前用户。但 ThreadLocal 最大风险是线程复用带来的脏数据，所以我在请求结束后做了 remove。

## 10.6 你怎么保证 AI 结果能落库

答法：

> 我没有直接让模型自由输出，而是通过 Prompt 约束字段结构，再指定 JSON 响应格式，最后后端再按对象反序列化。这样 AI 返回的结果更容易转成业务对象，也更适合后续统计分析。

## 10.7 AI 如果返回格式不对怎么办

答法：

> 当前主要依赖 Prompt 和 JSON 输出约束降低概率。更完善的方案我会补两层：一层是 JSON Schema 校验，一层是失败重试或兜底提示。这样不会因为一次模型输出漂移就影响主流程。

## 10.8 设备接入里最难的点是什么

答法：

> 难点其实不是调通 SDK，而是把云端设备模型映射到本地业务模型。因为系统不仅要知道设备存在，还要知道它绑定的是哪位老人、哪个房间、什么位置类型，以及设备数据怎么回流到本地系统。

## 10.9 设备注册如何保证不重复

答法：

> 注册前做了三层校验：设备名称唯一、节点号唯一、同一位置不能重复绑定同一产品。这样是为了防止运维混乱和业务关系冲突。

## 10.10 这个项目里有没有事务场景

答法：

> 有，护理计划和护理项目关系维护就是典型事务场景；入住申请本质上也是多表联动场景，涉及床位、老人、合同、入住记录、入住配置等数据协同。面试时我会重点强调“业务链路的一致性”。

## 15. 3 分钟深挖模板（推荐练熟）

如果面试官继续追问，你可以按这个顺序扩展：

### 15.1 业务背景

养老院需要统一管理老人入住、护理服务和健康数据，家属也希望能通过小程序查看信息和做预约。另一方面，老人健康评估和智能设备接入都是比较有价值的增量能力。

### 15.2 我负责的模块

我重点做了健康评估、小程序登录和 IoT 设备接入。

### 15.3 健康评估怎么做

用户先上传体检报告 PDF，后端上传 OSS 后把 PDF 解析成文本，并按身份证号暂存到 Redis。提交评估时，我根据身份证号取出报告内容，拼接强约束 Prompt 调用百度千帆，要求只返回 JSON。然后我把 AI 输出反序列化成对象，并落库保存健康分数、风险等级、异常分析和护理等级建议。

### 15.4 技术难点

最大的难点不是“调 AI”，而是让 AI 输出能稳定接进业务系统，所以我在 Prompt 里把字段格式固定下来，并且把确定性的业务规则仍然留在后端，比如根据分数映射护理等级。

### 15.5 另外两个模块

小程序登录用的是微信 `code -> openid -> 手机号 -> JWT` 链路，请求进入后通过拦截器解析 token，把用户 ID 放进 ThreadLocal。  
IoT 设备接入则对接华为云 IoTDA，既支持产品同步和设备注册，也支持通过 AMQP 异步接收设备上报数据。

### 15.6 我对这个项目的理解

这个项目不是特别重架构的项目，但它很适合体现业务理解、第三方平台接入能力以及把 AI/IoT 能力落到业务场景中的工程能力。

## 16. 最后给自己的复盘口径提醒

### 一定要讲清楚

- 项目服务谁
- 你负责什么
- 用户操作后链路怎么走
- 为什么这么设计
- 遇到了什么难点
- 有什么真实优化点

### 一定不要乱讲

- 不要把没有的 SSE、微服务、多智能体强行说成已有能力
- 不要只背 Controller、Service、Mapper 三层结构
- 不要只说“用了 Redis 做缓存”，要说清缓存什么、为什么缓存、如何失效
- 不要只说“调用了 AI”，要说清为什么能稳定接到业务里

### 最稳的面试原则

> 代码细节可以记不住，但**业务目标、技术决策、权衡和结果**一定要讲清楚。
