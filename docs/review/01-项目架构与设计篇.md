```java
// zzyl-framework Redis配置
@Configuration
@EnableCaching
public class RedisConfig {
    @Bean
    public RedisTemplate<Object, Object> redisTemplate(RedisConnectionFactory factory) {
        RedisTemplate<Object, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);
        // 使用Jackson2JsonRedisSerializer序列化
        Jackson2JsonRedisSerializer<Object> serializer = 
            new Jackson2JsonRedisSerializer<>(Object.class);
        template.setValueSerializer(serializer);
        template.setKeySerializer(new StringRedisSerializer());
        return template;
    }
}
```

#### 📖 详细解析

**1. 模块职责分析**：

| 模块 | 职责 | 依赖关系 |
|------|------|---------|
| `zzyl-admin` | 作为启动入口，聚合所有模块 | 依赖所有业务模块 |
| `zzyl-framework` | 框架级能力（Security、拦截器、Redis配置） | 被admin依赖 |
| `zzyl-common` | 公共能力（工具类、AI封装、异常处理） | 被所有模块依赖 |
| `zzyl-nursing-platform` | 核心业务（老人、床位、设备、健康评估） | 依赖common、framework |
| `zzyl-system` | 系统管理（用户/角色/菜单等RBAC权限） | 依赖common |
| `zzyl-quartz` | 定时任务（合同状态自动更新） | 依赖nursing-platform |
| `zzyl-oss` | 文件存储（对接阿里云OSS） | 依赖common |

**2. 现有设计优点**：
- ✅ 模块职责清晰，边界明确
- ✅ 公共层和框架层分离，便于复用
- ✅ 业务层独立，便于后续拆分

**3. 改进建议**：
- 💡 可考虑将 `zzyl-common` 的AI封装移到独立的 `zzyl-ai` 模块
- 💡 IoT设备管理可独立为 `zzyl-iot` 模块
- 💡 引入API网关模块 `zzyl-api` 统一对外接口

```java
@Transactional
public void checkIn(CheckInDto checkInDto) {
    // 1. 更新床位状态
    Bed bed = bedMapper.selectById(checkInDto.getBedId());
    bed.setStatus(BedStatus.OCCUPIED);
    bedMapper.updateById(bed);
    
    // 2. 创建/更新老人档案
    Elder elder = elderMapper.selectById(checkInDto.getElderId());
    elder.setStatus(ElderStatus.CHECKED_IN);
    elderMapper.updateById(elder);
    
    // 3. 创建合同
    Contract contract = new Contract();
    contract.setElderId(checkInDto.getElderId());
    contract.setContractNo(generateContractNo());
    contractMapper.insert(contract);
    
    // 4. 写入入住记录
    CheckIn checkIn = BeanUtil.toBean(checkInDto, CheckIn.class);
    checkInMapper.insert(checkIn);
    
    // 5. 写入入住配置
    CheckInConfig config = new CheckInConfig();
    configMapper.insert(config);
}
```

#### 📖 详细解析

**1. 为什么选择单体架构**：

| 维度 | 分析 |
|------|------|
| **业务复杂度** | 养老业务是一个完整的业务域，模块间耦合度高 |
| **部署简单** | 一个应用、一个数据库，运维成本低 |
| **开发效率** | 本地调试方便，事务一致性天然保证 |
| **团队规模** | 中小团队，微服务管理成本高于收益 |
| **性能足够** | 当前用户量和并发量不需要微服务级别的扩展 |

**2. 微服务拆分时机判断**：

```
判断是否需要微服务
         |

                    v             v

                                 | 是          | 否
                                 v             v

                                 |

                    +-------------------------+
                    | 1. IoT设备服务          |
                    | 2. AI分析服务           |
                    | 3. 用户认证服务         |
                    +-------------------------+
```

**3. 如果要拆分的建议**：
- 🥇 第一步拆出：**IoT设备服务**（调用频率高、独立性强）
- 🥈 第二步拆出：**AI分析服务**（计算密集、可异步）
- 🥉 第三步拆出：**用户认证服务**（通用性强）

#### 📖 详细解析

**1. 数据结构选择原则**：

```
选择数据结构
      |
      v
+-------------------------+
| 需要按维度快速定位?      |
+-------------------------+
     | 是          | 否
     v             v
  [Hash结构]  +-------------------------+
              | 需要整体取出?            |
              +-------------------------+
                   | 是          | 否
                   v             v
               [String结构] +-------------------------+
                            | 需要保持顺序?            |
                            +-------------------------+
                                 | 是          | 否
                                 v             v
                              [List结构] +-------------------------+
                                         | 需要去重/排序?           |
                                         +-------------------------+
                                              | 是          | 否
                                              v             v
                                           [Set/ZSet结构]  [其他]
```

**2. Key命名规范**：
- 格式：`业务模块:数据类型:具体标识`
- 示例：
  - `nursingLevel:all` - 护理等级全部数据
  - `iot:device_last_data` - IoT设备最新数据
  - `healthReport` - 健康报告（历史原因未完全遵循）

**3. 缓存一致性策略**：

| 策略 | 适用场景 | 优缺点 |
|------|---------|--------|
| **旁路缓存** | 读多写少 | ✅简单可靠 ❌极端情况不一致 |
| **双写模式** | 强一致性要求 | ✅一致性好 ❌代码复杂 |
| **消息通知** | 分布式场景 | ✅最终一致 ❌增加组件 |

**本项目选择**：旁路缓存模式（读缓存 → 未命中查DB → 回填缓存；更新DB → 删除缓存）

**参考回答**：
> "Redis主要用在四个场景：
> 1. 健康评估：缓存体检报告PDF内容，Hash结构按身份证号索引，24小时过期
> 2. IoT设备：缓存产品列表（String）、设备最新数据（Hash）
> 3. 基础数据：缓存护理等级、护理项目等读多写少数据
> 4. 认证相关：验证码、登录Token等
> 
> 数据结构选择：Hash用于需要按维度快速定位（如身份证号、iotId），String用于需要整体取出（如产品列表）。
> 
> 一致性策略采用旁路缓存模式：更新数据库后删除缓存而非更新缓存，避免并发更新导致脏数据。"

**追问应对**：

```

A: 删除更简单，避免并发更新导致脏数据，下次读取时再回填

Q: 缓存过期了怎么办？
A: 体检报告24小时过期，用户重新上传；基础数据没有过期，主动更新时删除

Q: Hash和String怎么选？
A: 需要按Field快速定位选Hash，需要整体取出选String
```

#### 📖 详细解析

**1. 索引设计原则**：

```
索引设计
    |
    +-- 选择性高的列优先 --> 如: 身份证号、iotId
    |
    +-- 高频查询列优先 --> 如: status、bed_id
    |
    +-- 复合索引遵循最左匹配 --> 如: location+product组合
    |
    +-- 避免过度索引 --> 写入性能下降
```

**2. 索引类型选择**：

| 索引类型 | 适用场景 | 示例 |
|---------|---------|------|
| **唯一索引** | 需要唯一性保证 + 高频查询 | 身份证号、iotId |
| **普通索引** | 筛选条件 | status、bed_id |
| **复合索引** | 多列组合查询 | 位置+产品组合 |
| **全文索引** | 文本搜索 | 备注、描述字段 |

**3. 索引失效场景**：

```
索引失效场景
    |
    +-- 使用OR连接条件 --> "WHERE a=1 OR b=2"
    |
    +-- LIKE左模糊匹配 --> "LIKE '%xxx'"
    |
    +-- 对索引列使用函数 --> "WHERE YEAR(create_time)=2026"
    |
    +-- 类型转换 --> "字符串字段用数字查询"
    |
    +-- 复合索引不满足最左匹配 --> 索引(a,b,c), 查询条件是b=c
```

```java
// ContractStatusJob.java - 合同状态定时任务
@Slf4j
@Component
public class ContractStatusJob {

    @Autowired
    private IContractService contractService;

    /**
     * 每天凌晨1点执行，检查并更新合同状态
     */
    @Scheduled(cron = "0 0 1 * * ?")
    public void updateContractStatus() {
        log.info("开始执行合同状态更新定时任务...");
        
        try {
            // 1. 处理待生效合同
            handlePendingContracts();
            
            // 2. 处理已到期合同
            handleExpiredContracts();
            
            log.info("合同状态更新定时任务执行完成");
        } catch (Exception e) {
            log.error("合同状态更新定时任务执行失败", e);
        }
    }

    /**
     * 处理待生效合同 → 生效中
     */
    private void handlePendingContracts() {
        LocalDateTime now = LocalDateTime.now();
        
        // 查询状态为待生效且生效日期<=今天的合同
        LambdaQueryWrapper<Contract> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(Contract::getContractStatus, ContractStatus.PENDING.getCode())
               .le(Contract::getStartTime, now);
        
        List<Contract> pendingContracts = contractService.list(wrapper);
        
        if (CollUtil.isEmpty(pendingContracts)) {
            log.info("没有待生效的合同需要处理");
            return;
        }
        
        // 批量更新状态
        for (Contract contract : pendingContracts) {
            contract.setContractStatus(ContractStatus.ACTIVE.getCode());
            contractService.updateById(contract);
            log.info("合同[{}]状态已更新为生效中", contract.getContractNo());
        }
        
        log.info("已处理{}个待生效合同", pendingContracts.size());
    }

    /**
     * 处理已到期合同 → 已到期
     */
    private void handleExpiredContracts() {
        LocalDateTime now = LocalDateTime.now();
        
        // 查询状态为生效中且到期日期<=今天的合同
        LambdaQueryWrapper<Contract> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(Contract::getContractStatus, ContractStatus.ACTIVE.getCode())
               .le(Contract::getEndTime, now);
        
        List<Contract> expiredContracts = contractService.list(wrapper);
        
        if (CollUtil.isEmpty(expiredContracts)) {
            log.info("没有已到期的合同需要处理");
            return;
        }
        
        for (Contract contract : expiredContracts) {
            contract.setContractStatus(ContractStatus.EXPIRED.getCode());
            contractService.updateById(contract);
            log.info("合同[{}]状态已更新为已到期", contract.getContractNo());
        }
        
        log.info("已处理{}个已到期合同", expiredContracts.size());
    }
}

public enum ContractStatus {
    PENDING(0, "待生效"),
    ACTIVE(1, "生效中"),
    EXPIRED(2, "已到期"),
    TERMINATED(3, "已解约");
    
    private final Integer code;
    private final String name;
    
    // getter methods...
}
```

#### 📖 详细解析

**1. 定时任务选择**：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **Spring @Scheduled** | 简单，无需额外配置 | 重启丢失任务，无持久化 | 小规模、非关键任务 |
| **Quartz** | 持久化、集群支持、动态配置 | 配置复杂 | 生产环境 |
| **XXL-Job** | 分布式、可视化管理 | 需要部署中心 | 大规模分布式 |

**2. 任务设计原则**：
- ✅ **幂等性**：任务可重复执行，结果一致
- ✅ **异常处理**：捕获异常记录日志，不影响后续执行
- ✅ **性能考虑**：批量处理而非逐条查询
- ✅ **执行时间**：避开业务高峰期（凌晨执行）

**3. 分布式定时任务挑战**：

```
问题:
+-------------------+     +-------------------+     +-------------------+
| 重复执行          | --> | 多实例同时执行    | --> | 同一任务          |
+-------------------+     | 同一任务          |     | 数据重复处理      |
                        +-------------------+     +-------------------+

+-------------------+     +-------------------+
| 任务丢失          | --> | 某实例宕机        | --> | 任务未执行        |
+-------------------+     +-------------------+     +-------------------+

+-------------------+     +-------------------+
| 状态同步          | --> | 任务执行进度      | --> | 无法共享          |
+-------------------+     | 无法共享          |     +-------------------+
                        +-------------------+

解决方案:
+-------------------+     +-------------------+
| Quartz集群        | --> | 数据库锁协调      | --> | 任务执行          |
+-------------------+     | 任务执行          |     +-------------------+
                        +-------------------+

+-------------------+     +-------------------+
| 分布式锁          | --> | Redis/Zookeeper   | --> | 实现互斥          |
+-------------------+     | 实现互斥          |     +-------------------+
                        +-------------------+

+-------------------+     +-------------------+
| 任务调度中心      | --> | XXL-Job统一调度   | --> | 集中管理          |
+-------------------+     | 集中管理          |     +-------------------+
                        +-------------------+
```

> 1. 待生效合同：生效日期<=今天，更新为生效中

>

```
Q: 分布式环境下定时任务有什么问题？
A: 重复执行（多实例同时执行）、任务丢失（实例宕机）、状态同步问题

Q: 怎么解决？
A: Quartz集群（数据库锁协调）、分布式锁（Redis/Zookeeper）、任务调度中心（XXL-Job）

Q: 任务失败了怎么处理？
A: 记录日志、告警通知、失败重试机制、死信队列处理
```
